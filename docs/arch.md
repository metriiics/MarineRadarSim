# Архитектура приложения

## 1. Назначение

Локальное desktop-приложение для подготовки студентов к работе с оригинальной системой **без наличия самой системы**.

Программа имитирует:

* рабочее место оператора;
* состояние системы;
* окружающую обстановку;
* работу датчиков/РЛС;
* реакцию системы на действия оператора;
* учебные ситуации;
* результаты выполнения заданий.

Приложение работает **автономно на одном ПК и без сети**.

---

# 2. Архитектурный принцип

**Modular Monolith.**

Все компоненты находятся в одном приложении.

```text
┌─────────────────────────────────────┐
│              GUI / Qt               │
├─────────────────────────────────────┤
│          Application Layer          │
├─────────────────────────────────────┤
│       Training / Assessment        │
├─────────────────────────────────────┤
│          Simulation Core            │
│                                     │
│ World                               │
│ Objects                             │
│ Motion                              │
│ Sensors / Radar                     │
│ System Model                        │
│ State                               │
└─────────────────────────────────────┘
                 │
                 ▼
          Local File Storage
```

Главный принцип:

> **Simulation Core не зависит от GUI и формата хранения данных.**

---

# 3. Presentation — пользовательский интерфейс

Технология: **Qt 6 Widgets**.

UI представляет виртуальное рабочее место оператора.

Основные области:

* основной рабочий экран;
* радиолокационное/тактическое отображение;
* органы управления;
* состояние системы;
* информация об объектах;
* сообщения и предупреждения;
* учебное задание;
* прогресс выполнения;
* результаты.

GUI отвечает только за:

* отображение состояния;
* ввод действий оператора;
* визуальную обратную связь.

GUI не содержит логики симуляции.

---

# 4. Application Layer

Связывает интерфейс с внутренней моделью.

Основные компоненты:

### Session Controller

Управляет текущим учебным занятием:

* Start;
* Pause;
* Resume;
* Reset;
* Stop.

### User Action Handler

Принимает действия студента и передаёт их в модель системы.

### State Provider

Получает текущее состояние Simulation Core и предоставляет его GUI.

### Training Controller

Управляет учебным заданием и его выполнением.

---

# 5. Training Module

Отвечает непосредственно за обучение.

### Training Session

Текущее занятие студента.

Содержит:

* учебную ситуацию;
* текущее состояние задания;
* действия студента;
* события;
* результат.

### Training Task

Определяет:

* что должен выполнить студент;
* начальные условия;
* требуемый результат;
* критерии правильного выполнения;
* допустимые действия;
* ошибки.

### Assessment

Проверяет:

* правильность действий;
* последовательность действий;
* время выполнения;
* ошибки;
* достижение требуемого состояния.

Assessment не изменяет физику симуляции.

---

# 6. Simulation Core

**Центр приложения.**

Отвечает за моделирование самой системы и окружающей обстановки.

## World

Моделируемый мир:

* объекты;
* координаты;
* время;
* окружающие условия.

## Objects

Моделируемые объекты:

* положение;
* скорость;
* движение;
* состояние.

## Motion

Модели движения объектов.

## Sensors / Radar

Моделирование работы датчиков:

* обнаружение;
* измерение;
* ошибки;
* шум;
* ограничения.

## System Model

Модель оригинальной системы.

Это один из ключевых компонентов.

Она определяет:

* внутреннее состояние системы;
* режимы работы;
* переходы между режимами;
* реакцию на действия оператора;
* ограничения;
* задержки;
* системные события.

## System State

Единое текущее состояние моделируемой системы.

GUI получает не внутренние объекты Simulation Core, а подготовленный **State Snapshot**.

---

# 7. Взаимодействие студента с системой

Основной цикл приложения:

```text
Студент
   ↓
Operator UI
   ↓
User Action
   ↓
Application
   ↓
System Model
   ↓
Simulation
   ↓
System State
   ↓
Operator UI
   ↓
Студент
```

Таким образом студент работает не непосредственно с моделью, а **через виртуальный интерфейс оригинальной системы**.

---

# 8. Simulation Clock

Используется фиксированный timestep.

Simulation работает независимо от частоты обновления GUI.

Это необходимо для:

* стабильности;
* воспроизводимости;
* тестирования;
* одинакового поведения учебных ситуаций.

---

# 9. Локальное хранение

**База данных в MVP отсутствует.**

Все данные находятся локально.

### Конфигурационные файлы

Используются для:

* учебных ситуаций;
* начальных условий;
* параметров системы;
* параметров объектов;
* параметров симуляции.

Формат: **YAML**.

### Результаты

Сохраняются в обычные локальные файлы.

Например:

```text
results/
    training_001.json
    training_002.json
```

Можно сохранять:

* действия студента;
* события системы;
* ошибки;
* время выполнения;
* итог задания;
* оценку.

### Runtime State

Во время работы хранится **в оперативной памяти**.

---

# 10. Потоки выполнения

Для MVP достаточно:

```text
GUI Thread
     │
     ▼
Simulation Thread
```

### GUI Thread

* интерфейс;
* ввод;
* визуализация.

### Simulation Thread

* simulation clock;
* World;
* Motion;
* Sensors;
* System Model;
* обработка действий;
* обновление состояния.

При необходимости тяжёлые операции можно позже вынести в отдельные worker threads.

# 14. Ключевой принцип системы

Архитектура должна быть построена вокруг следующего цикла:

> **Студент выполняет действие → виртуальная система его обрабатывает → Simulation моделирует последствия → состояние системы изменяется → интерфейс показывает результат → учебный модуль оценивает действие.**

Поэтому в MVP **главными компонентами являются не база данных и не система экспериментов, а три вещи:**

**Operator UI + System Model + Simulation Core.**
